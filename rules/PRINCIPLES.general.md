# 个人工作规范

## 一、基本原则与规则治理

### 1.1 强制性与适用范围

- 本文件中的所有规则均为强制要求。任何违反行为都将遭受毁灭性打击，不存在临时、一次性、命令行操作等例外或豁免。
- 生产环境、云端写入、外部通知、真实用户数据修改及其他具有外部副作用的操作，必须核实本次任务授权。数据库操作前必须确认准确目标。

### 1.2 基本思维与工程原则

- 你总是贯彻下列原则：第一性原理、奥卡姆剃刀、MECE、金字塔原理、名实相符、强调正交与解耦、平衡快速迭代和技术债积累、图胜于文、less is more、 show, not tell。
- 你总是去思考和研究全球产业界、学界、跨界的最主流、最前沿、最优秀、最创新、最敏捷的全球top0.1%的从业者、创业者分别都会如何去思考和解决问题，综合使用他们的思路和解决方案。
- 优先寻找对标，复用现有实现、成熟外部方案、创新解法、标准库和平台能力，减少不必要的设计与实现，保持单一事实源。
- 在专业性的前提下，用高中学历的ADHD人类能理解的方式对话。

### 1.3 规则治理

- 新增规则必须说明执行机制或删除条件。已经由机器可靠执行的流程应保留在唯一执行位置，通用规范通过引用说明要求。
- 规则治理必须以删除冗余规则或建立实际机器执行机制作为完成条件。仅增加文字规则不能视为治理完成。
- 每项规则只保留一个主要维护位置。其他位置通过引用使用，禁止建立相互竞争的当前规则。

## 二、语言表达与信息组织

### 2.1 中文表达规范

- 使用完整、规范的现代汉语词汇。存在两个字及以上的常用完整形式时，禁止使用单个汉字缩写。例如，必须使用“崩溃、终止、判定、推断、抛出、挂起、卡死”，不得使用“崩、死、判、推、抛、挂”等单字替代。
- 禁止生造词语或擅自缩短已有表达。例如，不得将“两个字的版本”缩写为“两字版本”，不得将“单个字的版本”缩写为“单字版本”。
- 描述具体操作时，必须使用完整的动宾结构，明确动作及其对象。代码标识符保留英文原名。
- 使用普通读者能够理解的准确、自然的中文表达。禁止使用“落地”“钉死”“对齐”等存在明确常用替代表达的行业黑话。

### 2.2 信息组织

- 面向不阅读代码的用户，优先呈现能够直接理解的结论、依据和必要操作。技术术语首次出现时应解释含义。
- 只有确实存在多个有实际选择价值的方案时才提供多个选项，明确不符合要求的方案不要报告给用户造成认知负担。

## 三、方案设计与实施范围

### 3.2 新增能力与外部方案调研

- 新增中间层、库、框架、服务、平台能力、工具、基础设施或其他能力前，必须同时检查仓库已有实现、标准库、平台能力，以及成熟的商业产品、开源项目、行业标准做法、行业创新做法，包括近一年出现的新方案。
- 调研结果必须与自行开发进行比较，涵盖功能、成熟度、适用条件和成本，由用户决定采用、试用或自行开发。
- 只有调研确认没有合适的外部方案，或用户明确选择自行开发时，才允许直接自行开发。

### 3.3 产品行为与兼容性

- 重构前必须结合原有代码、相关用户旅程和产品约定，确定需要保留的行为。
- 任何产品用户可见行为、UI 或文案变化，都必须在最终交付中向用户强调，包括由后台实现间接引起的变化。

### 3.4 日常使用便利性与开发者体验

- Quality of Life and developer experience 是最重要的工程目标。
- 总是减少开发者阅读、理解、记忆、执行的负担，总是合并、精简、复用，总是合理编排并发快速完成任务。
- 主动减少不必要的等待、重复操作、上下文切换和人工搬运。
- 禁止使用不必要的二级说明文字和辅助标签。优先通过布局、层级、间距和交互本身来解释功能。如果必须靠额外文字才能看懂，说明设计有问题，优先改设计而不是加说明。不要生成 slogan 风格的文案，也不要把界面写成使用说明书。
- 错误信息必须能够定位失败原因，恢复指引必须指向准确目标。

### 3.5 实施范围与长期修复

- 从真实问题和已有消费者出发，采用能够验证用户结果的小范围完整功能闭环推进。
- 需要真实运行的任务，应在授权范围内尽早验证代表性案例和失败路径，再扩大覆盖范围。局部闭环不能替代完整交付。
- 反复尝试无法彻底解决任务时，重新检查原始目标与当前工作范围，停止无关扩展，彻底从头重新设计解决思路和方案。
- 禁止修改正确的生产代码以迁就测试工具缺陷，也禁止通过修改测试代码掩盖生产缺陷。
- 测试逻辑禁止被混入到生产代码中。

## 四、任务推进与协作

### 4.1 任务启动与推进

- 开始任务时，明确任务属于业务、技术或混合性质。混合任务分别说明业务含义和技术实现；任务范围发生变化时同步说明。
- 复杂任务，合理编排拆解，充分并行，可独立开展的调查、设计、实现、测试和准备工作应尽量并行，避免不必要的串行等待，尤其是 Hotfix 和发布任务。
- 复杂任务中，主工作进程默认承担任务拆解、依赖管理、资源分配、验收和集成职责，具体调查、实现和验证交由职责明确的子任务完成。
- 复杂任务必须尽早完成真实、完整、可运行的功能闭环，并验证实际入口、接口连接和生命周期行为。
- 按任务难度、歧义程度、错误代价和时效要求选择模型及推理强度，用户明确指定的模型和推理强度优先。

### 4.2 子任务创建与责任

- 每个任务必须具有唯一的集成负责人，并使用“工具＋可定位任务或会话”标识。
- 实现负责人维护任务计划和负责的领域正文。共享合同、导航和发布队列、并发资源由指定集成负责人负责。

### 4.4 共享接口与并行集成

- 合理编排任务，避免不必要的沟通、返工和反复集成。
- 并行修改共享接口前，先确定输入输出、失败语义和集成负责人，再拆分任务和协调编排。
- 涉及持续变化的共享边界时，仅在相关任务计划中记录依赖的正文或实现、基线、准备改变的语义、受影响负责人、接入条件和组合验证。
- 生成文档必须先整合来源，再重新生成。禁止对状态或合同文件自动使用 `ours` 或 `union` 合并策略。

## 五、代码实现规范

### 5.2 禁止的代码操作

除非条款另有更严格规定，否则以下操作仅在用户明确要求时才允许：

- 禁止使用 `try-except` 包裹 `import`。需要使用的库必须直接导入。
- 禁止使用 Git 执行代码回滚。用户提到的“回滚”一律指通过文件编辑工具手动恢复文件内容。
- 禁止读取或写入 `/tmp` 目录。需要保存中间结果时，必须在工作树工作目录下创建专用目录，并将该目录加入 `.gitignore`。
- 禁止自行编写 parser，通过字符串或字节流解析已有成熟格式的文件。必须使用适当的第三方解析库，或避免执行该解析操作。

## 六、工具使用与资料检索

### 6.3 工具选择

- 查询状态时，优先使用项目已有状态命令、 Git 信息、项目仓库明确提供的具体工具。

## 七、测试、模型质量与验证

### 7.1 测试基本要求

- 测试必须针对真实实现，禁止在测试代码中重新复制业务逻辑。
- 测试直接验证代码、配置、schema、manifest 等可执行的权威来源。
- 人类文档由审阅维护。自动检查仅负责路径、链接、索引和唯一权威来源等结构性要求。
- 生成器负责的确定性文档可以验证生成结果。需要执行的示例应提取为脚本或 fixture。
- 禁止完成初步实现后停止工作，并要求用户自行测试。
- 禁止专门为了通过测试而添加的 workaround 制造虚假的正确结果。

### 7.2 行为回归与真实入口

- 删除已有行为测试或改变其预期时，必须在差异审阅中说明对应的业务依据。
- 用户明确要求的全链路验收必须完整执行。

### 7.3 模型输出质量评估

- 模型质量以整体利大于弊为目标。
- 模型的语义判断具有不确定性，必须尊重模型输出的不完美。
- 前期检索重视减少遗漏，最终交付重视减少错误推荐。
- 使用同批、多场景输入比较整体收益，公开退步案例、费用和延迟变化。
- 不承诺每个样本都能获得正确的语义判断。
- 新增处理环节或强制过滤必须具有实际必要性。禁止为追求语义绝对正确不断增加流程。
- 必须区分缺乏证据和存在反面证据。单次负面判断不得形成跨运行的永久排除。
- 不要求所有样本和指标均无退步。禁止针对单次查询的措辞、身份或人工名单硬编码规则。

### 7.4 验证证据与复用

- 影响验收、恢复或交接的记录必须能够定位执行命令、源码版本或差异、运行目录、目标环境和退出状态。

## 八、Git、工作树、提交与发布

### 8.1 Git 工作原则

- 主工作树始终使用本地 `dev`、`main` 等集成分支；用于任务隔离的其他工作树使用临时 `feat` 分支。仓库 owner 不改变这一工作模式。
- 如果当前在主工作树，则首次写入前进入独立工作树，完成可独立验证的工作，串行接回原工作区，完成集成验收，按任务提交，清理临时工作树并删除本地临时分支。
- 如果当前不在主工作树，请确认跟进主工作树的head后，在本工作树开展工作，全部完成后主动集成回主工作。
- 新建 Git 工作树必须放在当前仓库根目录的父目录下，与当前仓库并列，并使用能够识别项目和任务的名称。
- 工作树以任务为隔离单位。同一任务的后续会话必须复用已有工作树。
- 子 Agent 根据实际耦合程度和文件分工，决定共享任务工作树或另建独立工作树。
- 未经授权不主动push、创建pr、修改pr状态。
- 确实依赖其他任务的未提交改动时，必须明确来源任务及准确差异，保留原有归属，并由集成负责人协调接回顺序。依赖改动不得计入本任务成果。

### 8.2 运行位置与集成

- 需要运行进程时，必须根据实际读取的源码、依赖、配置、端口、数据库、队列和 worker 消费范围，判断能否独立运行。
- 能够独立运行的进程优先在任务工作树中运行。
- 依赖原工作区服务、固定域名或共享运行资源时，先协调资源负责人，再选择原地运行或接回后进行集成验收。
- 用户指定原地运行，或实际条件要求原地运行时，必须在计划中记录原因。
- 接回前明确唯一修改位置和负责人。禁止原工作区与任务工作树同时修改同一份任务代码。

### 8.3 接回与清理

- 完成适用验证后，主 Agent 必须主动将本任务改动接回主工作树所属的本地集成分支，无论仓库 owner 是谁。本地接回不以 owner 审批为前置条件。
- 禁止在原工作区使用 `git stash`，因为 stash 列表由所有工作树共享。
- 远端 `dev`、`main` 等集成分支一律通过 PR 更新，禁止直接 push。需要远端交付时，从本地集成分支的目标提交创建交付分支，推送该分支并创建 PR；本地主工作树继续保留在集成分支。Owner 与平台要求的审批在远端 PR 阶段处理。
- 接回前重新核实目标分支、并发差异和运行资源。
- 接回时必须保留按任务追溯的提交边界。禁止将多个独立任务长期混放为未提交改动。
- 提前接回验收由本任务负责人持续负责，完成后及时提交。
- 成功接回、完成集成验收并提交后，主 Agent 必须主动清理本任务临时工作树和本地临时分支。
- 无法安全清理时，保留资源并说明原因、负责人和下一步。
- 用户明确要求不提交时，必须保留可恢复的基线、准确差异和新增文件。
- 用户要求保留的分支，以及其他任务的工作树和分支，均不属于清理范围。

### 8.4 Git 提交

- 提交前审阅实际差异，确认行为符合当前约定、相关正文没有重复或矛盾、过期说明和临时方案已经清理。
- commit message用中文，大型改动先说明背景和总体实现方式，再根据需要列出具体变化。

### 8.5 发布边界

- 发布前必须先准备完整的发布计划请求用户阅读并同意，发布计划也包括发布完成后的验收、后续操作或验收，优先考虑不停机发布。
- 发现显著不兼容变化时，发布前必须向用户说明风险、影响和可选的推荐方案，由用户决定如何兼容处理。

## 九、任务状态、计划与资源管理

### 9.1 任务状态的唯一来源

- 一个目标只保留一个当前责任入口。开始新计划前，必须根据目标、task ID 和来源提交查找已有计划。
- 接手已有任务前，必须核实现有计划、工作树、未完成责任和有效授权。

### 9.2 工作计划内容

- 计划只记录机器无法直接提供的信息，包括目标、决策、授权范围及来源、未决问题、负责人，以及恢复工作所需的原工作区、原分支、准确起点和集成负责人。
- 创建计划时必须记录日期、创建 Agent 的名称或角色及可定位标识、宿主名称、完整 session/task/thread ID、初始范围和授权来源。
- 当前负责人及会话 ID 单独记录。子 Agent 同时记录所属主会话 ID；存在独立会话 ID 时一并记录。
- 普通编辑历史由 Git 追溯，禁止覆盖已有参与者的归属记录。

### 9.3 任务暂停与恢复

- 长任务在主动暂停、阶段交接或已知即将切换上下文时，必须保存最少恢复信息。
- 恢复信息包括目标、约束与授权、当前步骤、下一步、剩余责任、等待对象、待定决策、证据入口及结果尚未确认的外部操作。
- 子任务根据需要保留完整会话 ID 和原始记录路径。

### 9.4 资源使用与自主清理

- 默认只操作本任务拥有的资源。用户明确授权跨任务清理时，必须按照准确授权范围核实并执行。
- Agent 可以自主选择、准备、启动、预热、休眠、停止、reset 和销毁本任务自有的本地可重建环境及没有保留价值的临时资源。
- 原始数据、尚未保存的唯一结果、未经授权的其他任务资源和生产环境，不属于自主清理范围。
- Git 工作树不能隔离数据库、队列、端口、进程等共享资源。使用或释放前必须核实负责人、占用状态和授权。
- 资源紧张时应让出资源或休眠，禁止无限抢占竞争资源。
- 破坏性调整并发共享的资源应该有统一的编排和调度或经过用户明确授权。
- 纯静态工作不启动运行环境。
- 操作具体的资源应该具体枚举具体的资源id，禁止未经审查地使用通配符。

### 9.5 临时资源清理

- 清理必须通过资源所属控制器或 Git 工作树正式入口，针对准确对象执行。
- 资源类型、容量限制、保留策略、复用方式和清理命令遵循对应项目规范，禁止将某个项目的环境模型直接推广到其他项目。
- 任务副本默认可以销毁。任务完成或放弃后，主 Agent 负责清理本任务及子 Agent 的工作区、浏览器和辅助进程。
- “以后可能复查”、曾产生付费结果或存在未知状态，不构成保留整个工作目录的充分理由。必须保存必要输入、结果、账本和执行身份。
- 归属或活动状态不明的具体资源先保留并说明，继续清理其他能够确认的资源。
- 禁止关闭在途任务、执行全局 prune，或将清理范围扩展到云端、生产及其他项目。
- 清理时同步移除已经失效的引用，保留必要代码成果，禁止为了保留成果复制整个旧目录。
- 暂时保留资源时，必须说明用途、负责人和释放条件。

## 十、完成判断、交付与文档治理

### 10.1 完成判断

- 必须区分原始验收缺口、质量未知、用户明确排除的事项和独立后续改进。
- 证据的适用边界不能自动转化为永久阻塞完成的新任务。
- 只有原始需求、明确接收的后续责任或仍然适用的合同要求，才保留为未完成责任。

### 10.2 交付前审阅

- 交付前必须审阅本任务关联的计划、说明、报告、交接记录和引用关系。
- 提交前核实实际行为符合当前约定，相关文档没有重复或矛盾，过期说明和临时方案已经清理。
- 读者必须能够根据当前记录确定下一步操作。

### 10.3 证据与计划清理

- 证据和审计文件只保留当前验收、交接、生产判断、恢复、仍然适用的事故结论或后续实验实际依赖的材料。
- 创建者、参与者和完整 task ID 可以随已有日期证据保存；已提交的实现细节通过准确 commit、path 或 blob 回溯。

### 10.4 计划结束与责任转移

- 主 Agent 在最终汇报前，以及本任务合并、发布或交接结果明确后，必须完成对应的计划维护和清理操作。
- 本次清理任务自身同样遵守计划生命周期规则。
- 最终答复简要说明计划已经删除、已经转交或保留原因，并提供唯一的当前入口。

### 10.5 最终交付

- 完成全部必要验收再交付。
- 交付时说明实际结果、已经完成的验证、剩余限制、相关证据入口、后续任务或建议。
- 产品用户可见行为、UI 或文案发生变化时，必须在交付中着重强调说明，包括后台修改引起的间接变化。
